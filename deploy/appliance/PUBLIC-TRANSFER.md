# Public transfer plan

This document prepares a later milestone. It does not authorize a public
repository, image, tag, release or deployment change. Private acceptance and
the owner's explicit public-transfer acceptance must finish first.

## 1. Freeze and identify the private acceptance set

Record the exact accepted fork commit, selected Apache main ancestry, complete immutable
image ID, source/input manifests and local test receipts. Bind the real
deployment's catalog, network, release and runtime identities separately in
protected operator evidence. An image tag is not an acceptance identity.
Resolve or explicitly disposition each failed trial; a later passing run does
not establish the cause of an earlier timeout. Require both Windows targets,
native TOTP, chooser and direct links, SSH key/host verification, tmux process
continuity, independent restoration and matched rollback. A source test or
synthetic terminal test does not substitute for those live gates.

## 2. Review the complete history and artifact boundary

Review both the proposed public tree and every newly published commit and
blob relative to upstream. Check source archives, examples, documentation,
test fixtures, generated assets, build contexts and image layers. All instance
addresses, account names, authentication material, DATA, runtime captures,
private paths and owner-specific evidence must remain outside the public
history and artifacts. Synthetic examples must be clearly marked. Check
license/provenance for every included dependency, patch and fixture; preserve
Apache LICENSE, NOTICE, upstream history and required notices.

If private commits contain unsuitable material, prepare a clean publication
branch from the recorded upstream base and apply only reviewed generic
changes. Do not rewrite or destroy the accepted private history. Rebuild and
repeat affected acceptance for the proposed public source identity; private
receipts must not be relabeled as tests of different public bytes.

## 3. Rehearse the documented installation independently

Use a clean disposable host or VM with pinned prerequisites. A fresh reviewer
must follow the actual create/install/configure/backup/restore/rollback/remove
instructions without access to private operator notes. Include two synthetic
Windows/SSH targets as appropriate, failures of one target while another
remains usable, startup ordering and a real reboot. Record resource use,
exact versions, commands, expected outputs and all deviations as defects.
Prove that removal affects only owned resources and leaves unrelated host
services and tmux servers intact. Retain the verified recovery copy until
the owner separately retires it.

Current evidence includes a passing independent same-image host lifecycle
rehearsal with pre-enrolled synthetic DATA, native authentication, stopped
backup/independent restore, matched rollback, real reboot and exact owned
removal preserving unrelated services. Its catalog used documentation
endpoints, so it did not exercise target desktop or SSH sessions. A separate
operator-run fresh same-image installation passes actual Windows NLA/browser
access to both desktops over private loopback, with read-only Active-session
observations during stability holds and Disconnected sessions after cleanup.
An ensuing integrated run on the same clean VM passes both actual Windows
targets and a dedicated external synthetic SSH endpoint after initial install,
real portal reboot, independent stopped restore and matched rollback. Native
SSH refresh/reconnect retains the same external tmux/counter process identities.
An intentional first-route closure leaves the selected second desktop usable
through refresh. Exact owned removal preserves unrelated SSH/nginx, dedicated
guest tmux and firewall sentinel state; endpoint and tunnel cleanup pass.
Matched correct-pin/wrong-pin native controls establish certificate rejection
separately from the positive Windows browser checks.

This completes the integrated private lifecycle for the supported pre-enrolled
DATA boundary. It uses pinned prerequisites, operator-provided actual Windows
bindings and a synthetic dedicated SSH target. The finite fixture transport
has no installed transport service, so the optional additive-upgrade controller
was not exercised there: exact owned old network removal followed genuine
fresh mixed network preparation, retaining all original receipts and DATA.
Candidate selection and application removal are reviewed manual operations.
No generic fresh-user enrollment, unattended host installer, production reboot
or new-image production HTTPS acceptance follows from these private results.
Source transfer and a fresh build of the published main remain separate actions.

## 4. Define the supported product boundary

Document supported platforms, schema versions and upgrade paths; external
secret/data handling; TLS/reverse-proxy requirements; target labels and URL
grammar; key-only SSH and exact host pins; dedicated tmux socket behavior;
limits and unsupported account-isolation claims. Keep private host inventories
and production identifiers in operator memory, not product instructions.
Document retained single-use migration and failed-operation reconciliation
constraints explicitly. Name remaining manual installation/removal steps.

## 5. Prepare public automation without starting paid jobs

Review inherited workflows before enabling any automation. Start with bounded
local checks and an explicit hosted-minute budget. Use pinned dependencies and
least-privilege workflow permissions; never expose instance secrets to PR code.
Document the exact build/source manifests and reproducibility limits. Image
publication and signing need a separately reviewed destination and credentials.
Do not enable workflows or run paid jobs merely to reserve a future release.

## 6. Present a concrete owner acceptance package

Provide the intended public repository name, upstream base, final branch/commit,
reviewed diff and license inventory, test matrix with artifact identities,
deployment/recovery status, known limitations, proposed CI budget and exact
publication actions. Obtain explicit owner acceptance of that package before
creating the public repository or publishing any branch, tag or image.

## 7. Publish only the accepted set

Create the accepted repository/fork and push only the reviewed refs. Confirm
visibility and workflow settings before further pushes. Verify the public
commit/tree identities against the acceptance package. Build/publish only the
explicitly accepted immutable artifacts; verify downloaded digests and source
links. Keep operator instance files and migration data private. Publishing
source does not itself authorize switching an existing deployment.

## 8. Close the milestone with verifiable receipts

Record actual repository/ref/artifact URLs, immutable identifiers, workflow
outcomes and the tested installation commands. Update operator memory with
the retained rollback and recovery locations without putting them into public
documentation. Report precisely what was published and what remains private;
do not describe an unexecuted plan as a completed release.
